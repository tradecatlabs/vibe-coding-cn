# 修仙领域本体与分类设计（草案）

## 字多不看

- 本草案只服务修仙领域，不是全仓统一知识本体，也不要求其他学科改用 JSON。
- 已发布的 [V1 修仙解释图层](vibe-coding-cultivation-model.md) 仍只含七个基础对象；战力是具体任务的评价结果。
- “现实协作对象”和“关于知识的条目”分开建模；名称相同不代表对象相同。
- 知识条目暂用四类主类型与少量分面；心法、阵法、境界等只是领域内候选投影，不自动加入 V1。
- 先核对分类、关系和来源；目前不建立 JSON Schema、知识图谱服务或 Markdown 渲染器。

## 问题与边界

目标是判断：修仙领域中哪些**知识条目**值得结构化，如何不歪曲现有 V1 映射，并在需要时支持主题化展示。这不是把仓库里的教程、研究镜像、Skills、算子库和其他学科全部归一为同一套模型。

| 范围 | 当前边界 | 本草案的处理 |
|---|---|---|
| 现实协作映射 | 人类修士、万魂幡、魂魄、修为、灵力、功法、法器与任务战力 | 引用 V1 的定义，不重命名、不扩充七对象。 |
| 知识条目 | 对概念、方法、工具或失败方式的描述 | 设计仅在修仙领域生效的候选分类。 |
| 事实与来源 | 原始材料及固定事实镜像保持各自真相源 | 只引用可核对来源，不复制或改写固定镜像。 |
| 展示 | 现有手写 Markdown 仍可直接维护 | 主题投影只是未来候选；未建立生成管线前，不宣称 Markdown 已由 JSON 生成。 |

## 两种对象不能混为一谈

**现实协作映射**回答“修士、魂魄、功法、法器等在 AI 协作中分别指什么”。万魂幡是跨工具会话的概念集合；魂魄是单个会话，以来源与 Session ID 指认，不是 Memory。修为属于模型，战力属于有任务与验收条件的一次评价。

**知识条目**回答“这篇记录描述的知识是什么”。例如“Claude Code”条目描述一个工具，却不是一次 Claude Code 会话；“Agent Workflow”条目描述一种流程，也不会把 V1 中属于功法范围的 Workflow 改名为阵法。相同修仙名称在两个语境里出现时，必须标明是 V1 的现实映射，还是知识条目的主题标签。

本阶段不收集真实会话正文、凭据或其他人的数据；知识条目的存在也不授予任何工具使用权。

## 领域内知识条目的分类候选

每条知识记录先指定**一个主类型**，必要时再用分面描述差别；不为每个词新建一个顶层类型。

| 主类型 | 判定问题 | 可选分面 | 不应混入 |
|---|---|---|---|
| `concept` | 主要用于解释、判断或提出原则吗？ | `principle`、`mental_model` | 有可执行步骤的方法。 |
| `practice` | 主要描述可复用的做法吗？ | `methodology`、`technique`、`workflow` | 具体软件产品或一次执行结果。 |
| `tool_reference` | 主要介绍可调用的工具或接口吗？ | 暂不固定子类 | 真实会话、工具权限或 MCP 协议本身。 |
| `failure_mode` | 主要描述可观察的失败状态及其触发条件吗？ | 暂不固定子类 | 攻击技术、原因、症状之间未经证明的等同关系。 |

`kind` 只解决记录的主要职责；分面用于表达细节。来源、适用条件和不确定性与分类一起保存。工具的名称是被描述对象，不代表该条目允许调用它。

下表只展示**候选主题词**，不是新增 V1 基础对象，也不是全局类型映射：

| 知识记录分类 | 修仙展示候选 |
|---|---|
| `concept.principle` | 道则 |
| `concept.mental_model` | 心法 |
| `practice.methodology` | 功法 |
| `practice.technique` | 术法 |
| `practice.workflow` | 阵法 |
| `tool_reference` | 法器 |
| `failure_mode` | 劫难 |

不能因为条目用了“功法”或“法器”标签，就推断它与 V1 中某次会话使用的功法或法器是同一个实体。**境界**暂不分类：学习难度、个人掌握程度与战力评价是不同量，没有可靠口径前不把它们压成一条等级轴。

## 关系：先保留能解释的边

关系只连接本领域**知识条目 ID**。每种关系需要明确方向、适用类型、判定证据与反例；目标 ID 必须能解析。原文出处另存为来源证据，不用模糊的图谱边代替。

| 关系候选 | 方向与含义 | 不成立的情况 |
|---|---|---|
| `requires` | `practice → concept/practice`；缺少目标就无法正确理解或使用该做法。 | 只是“读过会更好”。 |
| `uses` | `practice → tool_reference`；方法定义本身依赖该工具。 | 某篇教程碰巧用 Claude Code 举例。 |
| `part_of` | `practice → practice`；来源是目标的组成部分，不允许组成环。 | 两种方法只是同时出现。 |
| `contrasts_with` | 同类条目之间有可说明的关键差异；双向表达。 | 只因为标签或领域相近。 |

`derived_from` 先作为有出处的内容溯源处理；`improves` 等声称效果的关系，需要任务对比证据，不能靠作者猜测自动补边。泛化的 `related_to` 暂缓，以免图谱只有连线、没有语义。

## 边界样例与反例

| 输入 | 本领域候选分类 | 需要守住的边界 |
|---|---|---|
| Context Engineering | `practice.methodology`，若条目描述完整方法体系 | 仅写单项操作时重新判为 `practice.technique`；不内在依赖 Claude Code。 |
| First Principles Thinking | `concept.mental_model`，待核对具体表述 | 如果条目主张的是规范原则，应重新判别，不因名字固定分类。 |
| Agent Workflow | `practice.workflow`，若条目描述有序协作步骤 | “阵法”仅是知识展示候选，V1 的 Workflow 仍属于功法映射范围。 |
| Claude Code | `tool_reference`，若条目主要介绍工具 | 工具说明不是魂魄，也不等于任何具体会话。 |
| AI Hallucination | `failure_mode` | 失败方式不是模型修为或任务战力的永久属性。 |
| Prompt Injection | **暂不归类** | 攻击手法不等于失败结果；若确需纳入，先证明现有类型为何不够。 |

分类依据条目实际主张，而非标题。这些只是分类判例，**不是已完成抽取、来源审查或条目入库**。无法判定时记录歧义，不用增加映射词或改写原意来让表格填满。

## 若进入结构化试点

先只在本领域试用最小语义记录：稳定 ID、主类型、必要分面、名称和定义、可追溯来源、经核实的关系，以及草稿/已审查状态。ID 不应把易变类型或展示名写死；类型调整需迁移记录，Schema 版本必须允许演化。来源不使用示例 URL 冒充真实证据。

主题名称与模板选择放在领域内的投影配置，不写成所有知识必须具备的语义字段。战力只记录与具体任务、验收条件、结果及投入绑定的评价证据，**不写成知识条目或模型的固定等级**。

试点只需要少量本仓自有条目，并故意包含 Prompt Injection 这样的反例。评审应能复核：类型判定不丢原意、关系目标可解析、来源能查回、V1 七对象与固定镜像不被改动。若多数样例靠特例才能分类，先收缩或修改本领域分类，而不是推广到全仓；只有分类稳定且出现实际生成需求时，再考虑领域内 JSON Schema 与确定性渲染。
