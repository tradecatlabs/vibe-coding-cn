# Vibe Coding 从入门到精通教程

> 用范畴论描述对象之间的变化，用复合组织行动，用交换图检查一致性，用对偶反向推理。

## 摘要

本文将 Vibe Coding 表述为一个以范畴论为根语言的工程模型：把输入、意图、目标、约束、状态、代码、文档、工具、结果和证据视为对象；把理解、生成、执行、适配、审查和验证视为态射；把计划与工作流视为态射复合；用交换图检查多条实现路径的一致性；用对偶从结果反推条件。该模型用于统一概念和组织行动，实际正确性仍由运行环境、权限、测试、审查和人工验收确认。

## 关键词

范畴论；对象；态射；复合；恒等态射；交换图；对偶；Vibe Coding；验证

## 1. 引言

### 1.1 问题背景

Vibe Coding 会同时涉及自然语言、模型、代码、命令、工具、权限、测试和交付结果。经验一多，术语容易分散，流程也容易失去统一的输入、输出和验证标准。

本教程用范畴论提供一套共同语法：对象说明正在处理什么，态射说明发生了什么变化，复合说明多个步骤如何连接，交换图说明不同路径是否保持一致，对偶说明如何从结果反向检查条件。

### 1.2 研究范围

本文只保留范畴论作为底层理论，并将它用于 Vibe Coding 的概念组织和工程表达。范畴论负责说明关系、方向和组合方式；模型、运行时、工具、权限、测试与人工验收负责产生和确认现实结果。

本文使用工程映射来帮助理解，不把每条工程经验直接宣称为数学定理。需要严格证明时，应单独给出定义、假设、命题、证明和适用范围。

### 1.3 阅读路径

先阅读第 2 节的范畴论预备知识，再阅读第 3 节的对象—态射模型；第 4 节解释五个基础认识，第 5 节展示运行路径，第 6 节给出验证要求，第 7 节说明适用边界。

## 2. 预备知识

### 2.1 范畴的基本语法

本节只介绍后文会用到的词汇。先记住：对象是正在处理的东西，态射是有方向的变化，复合是步骤连接，恒等态射是原样保持，交换图是路径一致，对偶是反向观察。

| 概念 | 直白理解 | 在 Vibe Coding 中的对应 |
|:---|:---|:---|
| 对象 | 正在处理的东西 | 输入、目标、约束、状态、代码、文档、结果、证据 |
| 态射 | 从一个对象到另一个对象的有向变化 | 理解、生成、执行、适配、审查、验证 |
| 复合 | 按顺序连接多个变化 | 计划、工作流、工程闭环 |
| 恒等态射 | 对象到自身且结构保持不变 | 保持输入、约束和结构 |
| 交换图 | 多条路径满足同一结果关系 | 需求、代码、测试和交付结果保持一致 |
| 对偶 | 将方向反转后重新观察 | 从结果回推条件，从失败追溯原因 |

### 2.2 对象与态射

对象回答“当前处理什么”，态射回答“发生什么变化”。每个态射都要有明确起点、终点和变化内容：

```text
输入对象 ──态射──→ 输出对象
```

如果 `f: A → B`，`g: B → C`，先执行 `f` 再执行 `g`，可以复合为 `g ∘ f: A → C`。复合满足结合律，工程上表示步骤的组合方式不应改变规定的整体结果。

恒等态射 `id_A: A → A` 表示从对象 `A` 指向自身且结构不变，并满足：

```text
id_B ∘ f = f = f ∘ id_A
```

### 2.3 交换图

从同一输入到同一目标存在多条路径时，各路径的复合结果应符合同一约定：

```text
A ──f──→ B
│        │
h        g
│        │
↓        ↓
C ──k──→ D
```

当 `g ∘ f` 与 `k ∘ h` 按验收标准得到同一结果时，图交换。需求、代码、类型、schema、测试、CI 和检查清单，都可以用来固定这个一致性要求。

### 2.4 对偶

范畴论中的对偶，是把所有态射方向反转后得到的对应结构。本教程用它组织反向工作：从目标回推条件，从输出追溯输入，从失败结果定位失效态射，从验收标准反推执行路径。

## 3. 对象—态射模型

### 3.1 对象分类

| 对象 | 作用 | 例子 |
|:---|:---|:---|
| 输入对象 | 提供问题的原始材料 | 需求、代码、数据、错误日志 |
| 目标对象 | 说明希望达到的状态 | 功能、结果、质量标准 |
| 约束对象 | 限定可行范围 | 时间、权限、技术栈、安全规则 |
| 中间对象 | 承载过程中的结构 | 计划、任务、配置、候选方案 |
| 结果对象 | 表示行动后的变化 | 代码、文档、部署状态、业务结果 |
| 证据对象 | 支持结果判断 | 测试输出、日志、diff、CI 状态 |

### 3.2 态射分类

| 态射 | 输入 | 输出 | 主要问题 |
|:---|:---|:---|:---|
| 理解 | 原始输入 | 目标与约束 | 是否准确理解问题 |
| 生成 | 目标与上下文 | 候选方案 | 是否生成可表达的方案 |
| 执行 | 候选方案与权限 | 状态变化 | 是否真实改变了系统 |
| 适配 | 外部接口与内部模型 | 边界内结构 | 是否隔离外部变化 |
| 验证 | 结果与验收标准 | 证据与结论 | 是否满足规定条件 |

### 3.3 工作流是态射复合

计划、工作流和工程闭环都可以表示为态射复合：

```text
输入 → 理解 → 计划 → 生成 → 执行 → 结果 → 验证
```

每一步的输出都应成为下一步可识别的输入。缺少起点、终点或验证条件的步骤，无法形成可检查的复合路径。

## 4. Vibe Coding 的五个基础认识

### 4.1 先解决人工智能问题

> **Demis Hassabis：“首先解决人工智能问题，然后再用人工智能解决其他所有问题”**

这条原则要求先把 AI 协作链跑通：人明确目标和约束，模型提出候选方案，Harness 调用工具执行，测试和人工验收确认结果。协作链稳定后，再把 AI 用于编程、写作、分析、研究和自动化。

用范畴论表示，就是先建立从人的意图对象到可执行对象的可靠复合路径，并为这条路径保留验证态射。

### 4.2 生成域

大语言模型直接生成符号对象。给定词表、上下文和工具协议后，模型能够表达的对象与调用路径构成其生成域。这里的生成域只描述模型能写出的内容，不包含执行权限。

模型能写出代码或命令，只说明候选描述已经生成；语法、语义、环境、权限和实际结果仍需单独验证。

> **可生成表示候选路径存在，可执行和有效需要额外证据。**

### 4.3 模型吞噬

Prompt 技巧、工作流、Agent 编排、索引、外部记忆、脚手架、工具封装和人工流程，都可以看作连接输入与结果的中间态射。

“吞噬”指模型能力增强后，原本由这些中间层承担的部分工作可能被模型直接处理。外部边界、权限控制和独立验证仍承担不可替代的职责。

### 4.4 隔离审查

生成结果是候选对象，审查是独立的验证态射。重要结果生成后，应开启新的审查会话，不沿用生成会话的结论，重新读取原始目标、约束、代码、文档和验证结果：

```text
原始目标 ──生成复合──→ 候选结果
    │                    │
    └──独立验证复合──────→ 证据与结论
```

### 4.5 能力编排

遇到需求时，先寻找成熟工具、库、平台和仓库提供的已有能力，把它们当作可复用的现成态射。拼好码负责连接、适配、编排和表达业务规则；只有关键约束无法满足时，才新增核心态射，并限定它的职责。

```text
需求对象 → 能力识别 → 成熟态射组合 → 适配边界 → 业务结果 → 验证证据
```

> **能复用时复合已有能力，能适配时保持边界，必须自研时限定新增职责。**

## 5. 总体运行模型

Vibe Coding 是把一个问题逐步变成已验证结果，并根据反馈继续修正的复合路径：

```text
现实问题 X
  ↓ 识别、描述、约束
目标结构 S
  ↓ Model：理解、推理、生成
候选方案 C
  ↓ Harness：上下文、工具、权限、执行循环
结果状态 S'
  ↓ 观察、测试、审查、记录
证据 E
  ↺ 反馈：修正目标、约束、计划与行动
```

把每一步写成态射：

```text
X ──I──→ S ──M──→ C ──T──→ S' ──V──→ E
```

- `X`：现实中的问题或原始输入。
- `I`：识别、描述和形式化输入的态射。
- `S`：目标、对象、约束和计划组成的结构。
- `M`：Model 生成候选方案的态射。
- `C`：待执行的候选方案。
- `T`：由 Harness、工具和权限组成的执行态射复合。
- `S'`：执行后的系统状态。
- `V`：测试、审查和质量门禁组成的验证态射。
- `E`：可追溯的验证证据。

Model 负责生成符号和行动意图；Harness 负责把候选意图接入工具、权限和执行循环；证据负责说明结果是否成立。

## 6. 验证与工程约束

### 6.1 每条态射都要有契约

至少写清以下内容：

- 输入对象是什么。
- 输出对象是什么。
- 前置条件是什么。
- 后置条件是什么。
- 失败路径是什么。
- 使用什么证据判断成功。

### 6.2 把交换条件落成机器门禁

能被确定性检查的要求，应写成测试、类型、schema、脚本、CI 或检查清单。机器门禁负责拦截路径不一致、依赖缺失、链接失效、配置错误和没有验收证据的结果。

### 6.3 人、模型与运行时的职责

1. **人负责方向。** 确定目标、价值、约束、取舍和最终判断。
2. **Model 负责候选。** 理解上下文、推理、生成方案和提出行动意图。
3. **Harness 负责执行。** 管理上下文、工具、权限、记忆、执行循环和反馈。
4. **机器负责校验。** 按确定性规则检查结果，并在条件不满足时失败。

### 6.4 顶层判断

1. 先识别对象，再确定态射。
2. 每个动作都写清起点、终点和失败路径。
3. 用复合组织计划、工作流和工程闭环。
4. 用交换图检查需求、代码、测试、文档、配置和结果的一致性。
5. 用对偶从结果回到条件，从失败回到失效环节。
6. 用证据确认结果，避免只依据模型的口头保证。

## 7. 讨论与适用边界

### 7.1 范畴论承担什么职责

范畴论为本项目提供统一的描述语言，帮助我们识别对象、标记变化、连接步骤、比较路径和组织反向检查。

### 7.2 范畴论不承担什么职责

范畴论本身不能替代程序运行、权限判断、测试执行、性能测量、安全审查或人工验收。一个形式上清楚的态射，仍然需要现实证据证明它能够运行并产生预期结果。

### 7.3 使用原则

- 先把真实对象和边界写清，再引入符号。
- 先说明输入、输出和验证，再讨论抽象结构。
- 只保留能帮助组合、检查或反向追溯的概念。
- 发现抽象无法解释实际行为时，回到输入、环境、权限和结果重新检查。

本教程的核心路径可以压缩为：

```text
对象 → 态射 → 复合 → 交换图 → 对偶审查 → 证据
```

本分支把范畴论作为根结构：对象承载问题与结果，态射表达变化，复合组织行动，恒等保持结构，交换图检查一致，对偶支持反向推理。

范畴论负责描述关系和一致性；运行环境、工具、权限、测试和人工验收负责确认结果。两者共同构成可执行、可检查、可回溯的 Vibe Coding 闭环。
