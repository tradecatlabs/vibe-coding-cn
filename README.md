# Vibe Coding 从入门到精通教程

**作者：** tukuai（独立研究者）
**文档定位：** 以范畴论为根语言的 Vibe Coding 工程教程
**当前版本：** `minimal`

## 摘要

本文以范畴论为根语言，建立 Vibe Coding 的统一工程模型。输入、意图、目标、约束、状态、代码、文档、工具、结果和证据被表示为对象；理解、生成、执行、适配、审查和验证被表示为态射；计划与工作流被表示为态射复合；交换图用于检查不同实现路径的一致性；对偶用于从结果反向追溯条件。该模型只负责统一概念、表达关系和组织行动，实际正确性仍由运行环境、权限、测试、审查和人工验收确认。

## 关键词

范畴论；Vibe Coding；对象—态射；态射复合；工程验证

## 1. 引言

### 1.1 问题背景

Vibe Coding 同时涉及自然语言、模型、代码、命令、工具、权限、测试和交付结果。术语增多后，经验容易分散，流程也容易失去统一的输入、输出和验证标准。

本文引入范畴论的基本语法，把这些内容放入同一套关系中：对象说明正在处理什么，态射说明发生了什么变化，复合说明多个步骤如何连接，交换图说明不同路径是否保持一致，对偶说明如何从结果反向检查条件。

### 1.2 研究目标

本文解决四个问题：

1. 如何用一套最小概念描述输入、操作、结果和证据。
2. 如何把 Model、Harness、工具、权限和验证放入同一条执行路径。
3. 如何用复合、交换图和对偶组织 AI 协作经验。
4. 如何把抽象关系落成契约、测试、脚本、schema 和 CI 门禁。

### 1.3 方法与范围

本文将范畴论用于工程建模和概念整理，不把工程映射直接当作数学定理。需要严格数学证明时，应另行给出定义、假设、命题、证明和适用范围。

本文的阅读顺序为：第 2 节预备知识，第 3 节形式化模型，第 4 节基础认识，第 5 节运行模型，第 6 节验证约束，第 7 节讨论边界，第 8 节结论。

## 2. 预备知识

### 2.1 范畴的基本定义

**定义 2.1（范畴）。** 一个范畴 `C` 至少包含以下数据：

1. 对象集合或对象类 `Ob(C)`。
2. 对任意对象 `A`、`B`，存在态射集合 `Hom_C(A, B)`。
3. 对每个对象 `A`，存在恒等态射 `id_A: A → A`。
4. 对态射 `f: A → B` 和 `g: B → C`，存在复合 `g ∘ f: A → C`。

复合满足结合律，恒等态射满足：

```text
id_B ∘ f = f = f ∘ id_A
```

在本教程中，只使用这些基本结构来组织工程关系。

### 2.2 对象与态射

对象回答“当前处理什么”，态射回答“发生什么变化”。每个态射都要有明确起点、终点和变化内容：

```text
输入对象 ──态射──→ 输出对象
```

如果 `f: A → B`，`g: B → C`，先执行 `f` 再执行 `g`，可以复合为 `g ∘ f: A → C`。计划、工作流和工程闭环，都可以按这个方式理解。

### 2.3 交换图

**定义 2.2（交换图）。** 从同一输入到同一目标存在多条路径时，各路径的复合结果按同一约定成立，则称该图交换：

```text
A ──f──→ B
│        │
h        g
│        │
↓        ↓
C ──k──→ D
```

交换条件写为：

```text
g ∘ f = k ∘ h
```

在工程中，需求、代码、类型、schema、测试、CI 和检查清单，都可以用来固定交换条件。

### 2.4 对偶

**定义 2.3（对偶范畴）。** 将范畴中的所有态射方向反转，得到对应的对偶范畴。本文用对偶组织反向工作：从目标回推条件，从输出追溯输入，从失败结果定位失效态射，从验收标准反推执行路径。

## 3. Vibe Coding 的形式化模型

### 3.1 对象分类

在本文的工程模型中，主要对象如下：

- **输入对象：** 需求、代码、数据、错误日志和环境信息。
- **目标对象：** 希望达到的功能、状态和质量标准。
- **约束对象：** 时间、权限、技术栈、安全规则和资源边界。
- **中间对象：** 计划、任务、配置、接口契约和候选方案。
- **结果对象：** 修改后的代码、文档、部署状态和业务结果。
- **证据对象：** 测试输出、日志、diff、CI 状态和人工验收记录。

### 3.2 态射分类

主要态射包括：

- **理解态射：** 将原始输入转换为目标与约束。
- **生成态射：** 将目标与上下文转换为候选方案。
- **执行态射：** 在权限范围内将候选方案转换为状态变化。
- **适配态射：** 将外部接口转换为内部边界内的结构。
- **验证态射：** 将结果与验收标准转换为证据与结论。

### 3.3 Vibe Coding 过程

**定义 3.1（Vibe Coding 过程）。** 设：

- `X` 为现实问题或原始输入。
- `S` 为目标、对象、约束和计划组成的结构。
- `C` 为模型生成的候选方案。
- `S'` 为执行后的系统状态。
- `E` 为可追溯的验证证据。

则一次 Vibe Coding 过程可以表示为：

```text
X ──I──→ S ──M──→ C ──T──→ S' ──V──→ E
```

其中：

- `I`：识别、描述和形式化输入。
- `M`：Model 生成候选方案。
- `T`：Harness、工具和权限组成的执行复合。
- `V`：测试、审查和质量门禁组成的验证复合。

### 3.4 Agent 的工程构成

在本文的工程映射中，Agent 由 Model 与 Harness 共同构成：

- **Model：** 理解上下文、推理、生成候选内容和提出行动意图。
- **Harness：** 管理上下文、工具、权限、记忆、执行循环和反馈。

Model 提出候选方案，Harness 负责执行方案，验证证据确认结果。三者的职责应保持区分。

## 4. Vibe Coding 的五个基础认识

### 4.1 先解决人工智能问题

> **Demis Hassabis：“首先解决人工智能问题，然后再用人工智能解决其他所有问题”**

这条原则要求先把 AI 协作链跑通：人明确目标和约束，Model 提出候选方案，Harness 调用工具执行，测试和人工验收确认结果。协作链稳定后，再把 AI 用于编程、写作、分析、研究和自动化。

用范畴论表示，就是先建立从人的意图对象到可执行对象的可靠复合路径，并为这条路径保留验证态射。

### 4.2 生成域

给定模型 `M`、上下文 `K` 和工具协议 `P`，模型能够表达的符号序列、结构化内容和工具调用路径，可以组成工程意义上的生成域 `G(M, K, P)`。

生成域只描述模型能够表达的候选内容。代码或命令进入生成域，仍需经过语法、语义、环境、权限和实际结果验证。

> **可生成表示候选路径存在，可执行和有效需要额外证据。**

### 4.3 中间态射的吸收

Prompt 技巧、工作流、Agent 编排、索引、外部记忆、脚手架、工具封装和人工流程，都可以看作连接输入与结果的中间态射。

当模型能力增强后，原本由中间层承担的部分工作可能被模型直接处理。若替换或压缩中间层不会破坏外部边界、权限控制和独立验证，则可以减少中间对象；仍承担独立职责的部分应继续保留。

### 4.4 隔离审查

生成结果是候选对象，审查是独立的验证态射。重要结果生成后，应开启新的审查会话，不沿用生成会话的结论，重新读取原始目标、约束、代码、文档和验证结果：

```text
原始目标 ──生成复合──→ 候选结果
    │                    │
    └──独立验证复合──────→ 证据与结论
```

### 4.5 能力编排

遇到需求时，先寻找成熟工具、库、平台和仓库提供的已有能力，把它们当作可复用的现成态射。拼好码负责连接、适配、编排和表达业务规则；只有关键约束无法满足时，才新增核心态射，并限定它的职责。

```text
需求对象 → 能力识别 → 成熟态射组合 → 适配边界 → 业务结果 → 验证证据
```

## 5. 总体运行模型

### 5.1 从问题到证据

Vibe Coding 是把一个问题逐步变成已验证结果，并根据反馈继续修正的复合路径：

```text
现实问题 X
  ↓ 识别、描述、约束
目标结构 S
  ↓ Model：理解、推理、生成
候选方案 C
  ↓ Harness：上下文、工具、权限、执行循环
结果状态 S'
  ↓ 观察、测试、审查、记录
证据 E
  ↺ 反馈：修正目标、约束、计划与行动
```

### 5.2 正向构造与反向审查

正向路径从输入构造结果：

```text
X ──I──→ S ──M──→ C ──T──→ S'
```

反向路径从验收标准和结果检查条件：

```text
E ←──V── S' ←──T── C ←──M── S ←──I── X
```

两条路径使用相同的对象和态射定义，便于发现输入丢失、边界漂移和验证缺口。

## 6. 验证与工程约束

### 6.1 态射契约

每条关键态射至少应写清：

1. 输入对象。
2. 输出对象。
3. 前置条件。
4. 后置条件。
5. 失败路径。
6. 成功证据。

### 6.2 交换条件与机器门禁

能被确定性检查的要求，应落成测试、类型、schema、脚本、CI 或检查清单。机器门禁负责拦截路径不一致、依赖缺失、链接失效、配置错误和没有验收证据的结果。

### 6.3 人、模型、运行时与机器

1. **人负责方向：** 确定目标、价值、约束、取舍和最终判断。
2. **Model 负责候选：** 理解上下文、推理、生成方案和提出行动意图。
3. **Harness 负责执行：** 管理上下文、工具、权限、记忆、执行循环和反馈。
4. **机器负责校验：** 按确定性规则检查结果，条件不满足时直接失败。

### 6.4 最小验证路径

```text
目标与约束
  → 候选方案
  → 执行结果
  → 独立审查
  → 机器门禁
  → 可追溯证据
```

缺少任一关键环节时，结果只能保留为候选状态，不能进入已验证状态。

## 7. 讨论与适用边界

### 7.1 范畴论的职责

范畴论为本项目提供统一的描述语言，帮助识别对象、标记变化、连接步骤、比较路径和组织反向检查。

### 7.2 工程验证的职责

范畴论本身不能替代程序运行、权限判断、测试执行、性能测量、安全审查或人工验收。形式上清楚的态射，仍需现实证据证明它能够运行并产生预期结果。

### 7.3 适用原则

- 先把真实对象和边界写清，再引入符号。
- 先说明输入、输出和验证，再讨论抽象结构。
- 只保留能帮助组合、检查或反向追溯的概念。
- 发现抽象无法解释实际行为时，回到输入、环境、权限和结果重新检查。

### 7.4 可证伪条件

出现以下任一情况时，应判定当前抽象或实现需要修正：

1. 无法明确指出态射的输入或输出。
2. 同一验收标准在不同路径上得到不一致结果。
3. 生成结果无法在目标环境中执行。
4. 验证依赖生成会话自己的口头结论。
5. 关键结果缺少可重复的测试、日志、diff 或其他证据。

## 8. 结论与完整仓库入口

本教程的核心路径可以压缩为：

```text
对象 → 态射 → 复合 → 交换图 → 对偶审查 → 证据
```

本分支把范畴论作为根结构：对象承载问题与结果，态射表达变化，复合组织行动，恒等保持结构，交换图检查一致，对偶支持反向推理。

范畴论负责描述关系和一致性；运行环境、工具、权限、测试和人工验收负责确认结果。两者共同构成可执行、可检查、可回溯的 Vibe Coding 闭环。

极简分支只保留这套根理论及其统一解释。需要完整教程、实践方法、工具配置、Skill、工作流和研究资料时，进入[完整仓库的 develop 分支](https://github.com/tradecatlabs/vibe-coding-cn/tree/develop)。
