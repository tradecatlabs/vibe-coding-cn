## 摘要

本文以范畴论为根语言，建立 Vibe Coding 的统一工程模型。输入、意图、目标、约束、状态、代码、文档、工具、结果和证据被表示为对象；理解、生成、执行、适配、审查和验证被表示为态射；计划与工作流被表示为态射复合；交换图用于检查不同实现路径的一致性；对偶用于从结果反向追溯条件。该模型负责统一概念、表达关系和组织行动，实际正确性仍由运行环境、权限、测试、审查和人工验收确认。

## 1. 引言

### 1.1 问题背景

Vibe Coding 同时涉及自然语言、模型、代码、命令、工具、权限、测试和交付结果。术语增多后，经验容易分散，流程也容易失去统一的输入、输出和验证标准。

本文引入范畴论的基本语法，把这些内容放入同一套关系中：对象说明正在处理什么，态射说明发生了什么变化，复合说明多个步骤如何连接，交换图说明不同路径是否保持一致，对偶说明如何从结果反向检查条件。

### 1.2 相关理论基础

范畴论以对象、态射、恒等态射和复合为基本结构，并通过结合律与恒等律约束组合方式 [1]。应用范畴论进一步强调复杂系统中的组合、接口和结构保持 [2]。本文借用这套语言描述 AI 协作流程，不扩张为未经证明的数学结论。

### 1.3 研究目标与贡献

本文的目标是建立一套最小、清晰、可验证的工程表达：

1. 用对象描述输入、目标、约束、状态、结果和证据。
2. 用态射描述理解、生成、执行、适配、审查和验证。
3. 用复合描述计划、工作流和 Agent 执行循环。
4. 用交换图、对偶和可重复证据约束 AI 协作质量。

本文提供工程模型和教程结构，不提出新的范畴论定理。

### 1.4 文章结构

第 2 节给出范畴论预备知识及其工程类比；第 3 节建立 Vibe Coding 的对象—态射模型；第 4 节说明 Vibe Coding 的五个基础认识；第 5 节描述运行路径；第 6 节给出形式推导与成立条件；第 7 节给出工程验证要求；第 8 节讨论适用边界；第 9 节总结全文；第 10 节列出致谢和附录，文末给出参考文献。

## 2. 预备知识

### 2.1 范畴的基本定义

**定义 2.1（范畴）。** 一个范畴 $\mathcal{C}$ 至少包含以下数据：

1. 对象集合或对象类 $\mathrm{Ob}(\mathcal{C})$。
2. 对任意对象 $A$、 $B$，存在态射集合或态射类 $\mathrm{Hom}_{\mathcal{C}}(A,B)$。
3. 对每个对象 $A$，存在恒等态射 $id_A:A\to A$。
4. 对态射 $f:A\to B$ 和 $g:B\to C$，存在复合 $g\circ f:A\to C$。

复合满足结合律：

$$
(h\circ g)\circ f=h\circ(g\circ f)。
$$

恒等态射满足：

$$
id_B\circ f=f=f\circ id_A。
$$

在本教程中，只使用这些基本结构来组织工程关系。

### 2.2 对象与态射

对象回答“当前处理什么”，态射回答“发生什么变化”。每个态射都要有明确起点、终点和变化内容。其中， $A$ 是定义域， $B$ 是陪域：

$$
A\xrightarrow{f}B。
$$

如果 $f:A\to B$， $g:B\to C$，先执行 $f$ 再执行 $g$，可以复合为 $g\circ f:A\to C$。计划、工作流和工程闭环，都可以按这个方式理解。

### 2.3 交换图

**定义 2.2（交换图）。** 从同一输入到同一目标存在多条路径时，各路径的复合结果按同一约定成立，则称该图交换：

```text
A ──f──→ B
│        │
h        g
│        │
↓        ↓
C ──k──→ D
```

交换条件写为：

$$
g\circ f=k\circ h。
$$

在工程中，需求、代码、类型、schema、测试、CI 和检查清单，都可以用来固定交换条件。

### 2.4 对偶

**定义 2.3（对偶范畴）。** 将范畴中的所有态射方向反转，得到对应的对偶范畴 $\mathcal{C}^{\mathrm{op}}$。其对象保持不变，且：

$$
\mathrm{Ob}(\mathcal{C}^{\mathrm{op}})=\mathrm{Ob}(\mathcal{C}),\quad \mathrm{Hom}_{\mathcal{C}^{\mathrm{op}}}(A,B)=\mathrm{Hom}_{\mathcal{C}}(B,A)
$$

本文用对偶组织反向工作：从目标回推条件，从输出追溯输入，从失败结果定位失效态射，从验收标准反推执行路径。对偶只改变描述方向，不声称原态射必然存在逆态射。

### 2.5 直观解释与类比

前面的定义给出了形式语言。为了把这套语言用于 Vibe Coding，可以从一个最小工程场景开始：用户用十几个字提出需求，最终得到数百行代码、一次真实执行和一组验收证据。需求在抵达结果之前，通常要经过目标、约束、文件、函数、命令、测试、运行状态和失败日志等多个中间对象。每一次从一个对象到另一个对象的有规则变化，都可以用一根箭头表示。

这里的类比用于帮助理解工程结构，不替代范畴的公理定义。它要求我们持续回答三个问题：当前对象是什么，变化由什么态射完成，结果由什么证据确认。

#### 2.5.1 对象：当前处理什么

可以把对象理解为“当前桌面上放着什么”。只要在当前分析边界内把某个整体作为一个单位处理，它就可以成为对象。对象可以是静态材料，也可以是某一时刻的系统状态。

常见对象包括：

- 人脑中的目标和业务问题。
- 用户输入、需求描述和验收标准。
- 计划、任务清单、接口契约和配置。
- Git 仓库、文件、函数、代码和数据。
- JSON、schema、数据库状态和 API 响应。
- 测试报告、运行日志、错误日志和 Git diff。
- 人工判断、CI 状态和最终交付结果。

例如，用户说“给这个项目加一个登录功能”，这句话可以先作为原始输入对象。AI 理解后形成的需求结构是另一个对象，修改后的代码又是另一个对象，测试结果和数据库状态仍然分别构成对象。对象的关键不在于它的物理形态，而在于它是否具有清晰的边界、身份和当前状态。

#### 2.5.2 态射：对象如何变化

对象本身只描述当前状态，态射描述从一个对象到另一个对象的变化：

```text
输入 ──变化──→ 输出
```

在 Vibe Coding 中，可以看到一条基本链：

```text
需求 ──理解──→ 计划
计划 ──生成──→ 候选方案
候选方案 ──执行──→ 系统状态
系统状态 ──验证──→ 证据
```

一根可用的工程箭头至少要说明四件事：

1. 输入对象是什么。
2. 输出对象是什么。
3. 中间执行了什么变换。
4. 失败时留下什么可追踪结果。

因此，“处理一下”还不足以描述一个明确态射。它没有给出输入边界、目标状态、执行动作和验收方式。把箭头画出来，遗漏的前提会暴露出来，模糊任务才有机会变成可执行任务。

**定义 2.4（工程态射契约）。** 对工程态射 $f:A\to B$，记其契约为：

$$
\Gamma_f=(\mathrm{Pre}_f,\mathrm{Post}_f,\mathrm{Fail}_f)
$$

其中， $\mathrm{Pre}_f$ 是前置条件， $\mathrm{Post}_f$ 是成功后的后置条件， $\mathrm{Fail}_f$ 是失败时必须保留的结果、错误或证据。只有当前置条件成立且输出满足后置条件时， $f$ 才能作为可靠的工程箭头参与后续复合。

若 $f:A\to B$ 与 $g:B\to C$ 需要复合，还必须检查 $f$ 的后置条件能够满足 $g$ 的前置条件。这个检查把“步骤顺序正确”提升为“相邻接口契约兼容”。

#### 2.5.3 复合：把变化连接成过程

假设一个 Agent 依次读取需求、查找文件、修改代码、安装依赖、运行测试、修复错误并重新测试。外部观察到的是一次任务，内部实际发生的是多根连续箭头：

```text
输入
  → 理解
  → 计划
  → 修改
  → 执行
  → 验证
  → 结果
```

若 $f:A\to B$， $g:B\to C$，且 $f$ 的输出确实满足 $g$ 的输入契约，则可以复合为：

$$
g\circ f:A\to C。
$$

工程中的工作流也必须满足这个条件：上一步的结果要成为下一步真正需要的输入，不能只在文档里按顺序排列。模型生成一次，工具执行一次，环境返回一次，模型再依据返回结果决定下一步，这个循环仍然是许多态射的复合。

复合还要求结合律成立：先组合前几步，或先组合后几步，最终过程的规定结果应保持一致。若不同分组改变了目标、约束或状态含义，流程就出现了漂移。

#### 2.5.4 恒等态射：传递时保持不变

恒等态射从对象 $A$ 回到对象 $A$：

```text
id_A: A → A
```

它表达一种工程要求：某些步骤承担保留职责，传递数据、约束或接口时不得偷偷改变其含义。

例如：

- 用户给出的日期经过多层调用后仍应保持原值和时区语义。
- schema 中约定的字符串经过适配层后仍应满足原契约。
- 用户要求保持的 API，重构完成后仍应保持兼容。
- 一个约束经过计划、实现和测试阶段后，仍应出现在最终验收中。

范畴论中的恒等关系为：

$$
id_B\circ f=f=f\circ id_A。
$$

工程上可以把它理解为“传递不能造成隐式改写”。Agent 在总结上下文时删掉一条限制，或者在适配数据时改变一个字段语义，后面的每个步骤即使执行正确，也可能共同完成了另一项任务。因此，边界字段、原始需求和不可变约束需要有显式保留检查。

#### 2.5.5 交换图：不同路径指向同一契约

当同一需求同时经过实现路径和验证路径时，可以用交换图检查它们是否仍然指向同一规定结果：

```text
A ──f──→ B
│        │
h        g
│        │
↓        ↓
C ──k──→ D
```

交换条件为：

$$
g\circ f=k\circ h。
$$

在工程里，这不要求两条路径生成完全相同的文本，而要求它们对同一个需求契约成立。例如，第一条路径把“退出登录后 token 失效”实现到代码中，第二条路径把同一要求编译成测试和 CI 检查；只有两条路径共同落到同一验收标准上，图才具有工程意义。

代码、类型、schema、测试、CI、检查清单和人工审查，都是固定交换条件的手段。它们把“这些内容应该一致”转化为可执行检查。代码和测试可以同时通过，但测试若验证了错误目标，图从一开始就没有交换；局部一致不能代替全局契约一致。

#### 2.5.6 对偶：从结果反向追溯

对偶把描述结构的箭头方向反转。它不表示现实因果关系真的倒转，而是提供一种反向检查方法：

```text
失败结果
  → 哪个验证器应该发现
  → 哪个执行动作产生状态
  → 哪个候选方案指导动作
  → 哪个目标与约束生成方案
  → 哪个输入造成最初歧义
```

正向过程用于建设：从问题描述走向交付结果。反向过程用于审查：从失败结果逐层寻找首个失效态射。做新功能时，也可以从最终交付物反推所需证据、测试、实现和输入对象，先确定如何证明，再确定如何建设。

这种反向方法能把“结果不对”变成可定位的问题链：验证规则可能错误，执行环境可能未更新，候选方案可能缺少约束，目标结构可能没有表达真正需求，最初的现实问题也可能尚未澄清。

#### 2.5.7 生成与执行：Model、Harness 与真实状态

在 Agent 系统中，模型首先生成符号和候选动作。Python、SQL、Shell、JSON、工具调用以及“已经完成”的文字报告，最初都属于模型能够表达的文本或结构。

生成结果只有在运行时进入真实环境，才可能造成状态变化。可以把完整路径写成：

```text
人的意图
  → 可理解的目标
  → 可执行的候选行动
  → 真实执行
  → 证据
  → 人或机器的判断
```

这里要区分两个层次：

- **Model：** 负责理解、推理、规划和生成候选文本或工具调用意图。
- **Harness：** 负责执行循环、上下文、工具、权限、状态、错误处理、重试和结果回写。

因此可以用一个简化关系表示：

```text
Agent = Model + Harness
```

写出 `pytest` 不等于测试通过，生成 SQL 不等于数据库已改变，模型报告文件已保存也不等于磁盘上存在该文件。候选动作必须经过 Harness 的权限边界和真实执行，再由验证器确认状态。

#### 2.5.8 证据：确认箭头确实抵达目标

工程闭环的末端应落在一组能够回溯到当前输入和当前状态的证据对象上；“完成”只是标签，不能替代证据：

- 测试结果和类型检查结果。
- schema、lint 和 CI 状态。
- 日志、截图、运行状态和 API 响应。
- Git diff、提交记录和人工验收记录。

证据要回答两个问题：事情是否真实发生，发生的是否正是原始目标要求的事情。自信的表述不会增加证据数量；只有可复现命令、独立检查和真实产物能提高结论强度。

因此，预备知识中的六个范畴论核心词，加上证据对象，可以在工程中扩展为一条检查线：

```text
对象 → 态射 → 复合 → 恒等 → 交换图 → 对偶 → 证据
```

对象说明当前有什么，态射说明发生了什么，复合说明变化如何连接，恒等说明哪些约束必须保持，交换图说明不同路径是否遵守同一契约，对偶说明如何从结果追溯原因，证据说明结论是否可被复核。第 3 节将在此基础上给出 Vibe Coding 过程的正式符号化表达。

### 2.6 工程模型的形式边界

本文把范畴论作为工程建模语言。选定对象、态射及其契约后，只有在以下条件成立时，相关结构才可以在给定抽象层次上按范畴处理：

1. 每个对象的边界和身份可以说明。
2. 每个态射具有明确的定义域和陪域。
3. 每个对象存在保持其结构的恒等态射。
4. 相邻态射只有在输入输出契约匹配时才能复合。
5. 复合满足结合律，重新分组不会改变规定的结果关系。

工程态射通常带有前置条件、后置条件、权限和外部副作用，也可能因环境或输入不同而失败。因此，本文的工程映射采用“在给定契约与环境下成立”的解释：范畴论负责表达可组合关系，运行时负责处理执行，验证器负责确认实际结果。形式上的可复合性不能单独推出程序正确性、部署成功或业务价值。公式中的 $\rightharpoonup$ 表示工程层的部分映射；若要构造严格的偏映射范畴，还需要把失败状态或偏域显式纳入对象与态射定义。

工程对象还带有版本和环境上下文。两个文本相同的对象，若来源版本、权限或运行环境不同，可能不属于同一个工程状态；两个文本不同的对象，也可能在某个契约下具有等价行为。后文的“相同结果”均指满足同一契约，不默认要求字节级或文本级相等。

在固定环境 $H$ 与契约 $\Gamma$ 下，可以把这套工程结构记为 $\mathcal{E}_{H,\Gamma}$：其对象是带版本和环境上下文的工程状态，其态射是带契约的状态变换。只有对象身份、态射端点、恒等态射、复合规则和结合律都明确时， $\mathcal{E}_{H,\Gamma}$ 才能作为本文意义上的工程范畴使用。

后文关于复合“存在”的表述，默认限定在各部分映射的成功域上；若要把失败结果也纳入同一范畴，必须显式扩展对象和态射，不能把失败静默视为普通输出。

本文区分任务级原始契约 $\Gamma$ 与单步态射契约 $\Gamma_f$：前者规定整个任务的目标、约束和验收标准，后者规定单个变换的输入、输出和失败条件。单步契约必须由任务级契约派生或与其保持一致，单步通过不能单独推出任务级契约满足。

## 3. 主体内容：Vibe Coding 的工程范畴模型

### 3.1 工程对象

在本文的工程模型中，主要对象如下：

- **输入对象：** 需求、代码、数据、错误日志和环境信息。
- **目标对象：** 希望达到的功能、状态和质量标准。
- **约束对象：** 时间、权限、技术栈、安全规则和资源边界。
- **中间对象：** 计划、任务、配置、接口契约和候选方案。
- **结果对象：** 修改后的代码、文档、部署状态和业务结果。
- **证据对象：** 测试输出、日志、diff、CI 状态和人工验收记录。

### 3.2 工程态射

主要态射包括：

- **理解态射：** 将原始输入转换为目标与约束。
- **生成态射：** 将目标与上下文转换为候选方案。
- **执行态射：** 在权限范围内将候选方案转换为状态变化。
- **适配态射：** 将外部接口转换为内部边界内的结构。
- **验证态射：** 将结果状态与原始契约转换为证据与结论。

### 3.3 Vibe Coding 过程的定义

**定义 3.1（Vibe Coding 过程）。** 设：

- $X$ 为现实问题或原始输入。
- $S$ 为目标、对象、约束和计划组成的结构。
- $C$ 为模型生成的候选方案。
- $S'$ 为执行后的系统状态。
- $\Gamma$ 为目标、约束和验收标准组成的原始契约。
- $E$ 为可追溯的验证证据。

则一次 Vibe Coding 过程可以表示为：

$$
X\xrightarrow{I}S\xrightarrow{M}C\xrightarrow{T_H}S'\xrightarrow{V_\Gamma}E。
$$

其中：

- $I$：识别、描述和形式化输入。
- $M$：Model 生成候选方案。
- $T_H$：在运行环境、Harness、工具和权限 $H$ 下执行候选方案。
- $V_\Gamma$：依据原始契约 $\Gamma$，由测试、审查和质量门禁组成的验证复合。

这些映射通常是带前置条件的部分映射：

$$
I:X\rightharpoonup S,\quad M:S\rightharpoonup C,\quad T_H:C\rightharpoonup S',\quad V_\Gamma:S'\rightharpoonup E。
$$

部分映射表示某一步可能因信息不足、权限不足、环境错误、执行失败或验证失败而无法完成。它不会把失败隐藏在“完成”标签后面。记 $E\models\Gamma$ 表示证据在给定环境和验证规则下满足契约 $\Gamma$。

记 $\mathrm{Ind}(V_\Gamma;\Gamma,S')$ 表示验证过程满足来源独立性：验证器重新读取原始契约 $\Gamma$，并直接检查结果状态 $S'$ 或其可追溯产物；验证结论必须建立在这些对象上，不能只依赖生成会话的自述。这个谓词描述证据的来源条件，不属于范畴公理，也不等同于“开启了新的会话”。因此，结果的模型内验证标记可写为：

$$
\mathrm{Verified}_\Gamma(S')\Longleftrightarrow\exists E\,[V_\Gamma(S')=E\land E\models\Gamma\land\mathrm{Ind}(V_\Gamma;\Gamma,S')]
$$

其中， $E\models\Gamma$ 是本文约定的项目验收关系；除非另行给出形式语义，它不表示由范畴论公理自动推出的逻辑蕴涵。

### 3.4 Agent 的工程构成

在本文的工程映射中，`Agent = Model + Harness` 是职责组合记号，不表示两个集合的严格等式：

- **Model：** 理解上下文、推理、生成候选内容和提出行动意图。
- **Harness：** 管理上下文、工具、权限、记忆、执行循环和反馈。

Model 提出候选方案，Harness 负责执行方案，验证器依据契约确认结果。三者的职责应保持区分。

## 4. Vibe Coding 的五个基础认识

### 4.1 先解决人工智能问题

> **Demis Hassabis：“首先解决人工智能问题，然后再用人工智能解决其他所有问题”** [3]

这条原则要求先把 AI 协作链跑通：人明确目标和约束，Model 提出候选方案，Harness 调用工具执行，测试和人工验收确认结果。协作链稳定后，再把 AI 用于编程、写作、分析、研究和自动化。

用范畴论表示，就是先建立从人的意图对象到可执行对象的可靠复合路径，并为这条路径保留验证态射。

### 4.2 生成域

给定模型 $M$、上下文 $K$ 和工具协议 $P$，模型能够表达的符号序列、结构化内容和工具调用路径，可以组成工程意义上的生成域 $G(M,K,P)$。该记号描述候选表示的范围，不能单独推出候选方案可执行或结果有效。

代码或命令进入生成域后，仍需经过语法、语义、环境、权限和实际结果验证。模型生成域、Harness 执行域和契约满足关系属于不同判断层次，必须分别取证。

“生成域”是本文为工程分析约定的术语，用于标记模型在给定条件下能够表达的候选范围；它不承担程序可执行性、运行权限或业务正确性的含义。

| 判断层 | 核心问题 | 典型对象或证据 |
|:---|:---|:---|
| 生成域 | Model 能否表达候选内容 | 代码、命令、结构化输出、工具调用意图 |
| 执行域 | Harness 能否在 $H$ 中执行并产生状态变化 | 文件 diff、进程状态、API 响应、运行日志 |
| 契约满足层 | 结果是否满足 $\Gamma$ | 测试、类型、schema、CI、审查和验收记录 |

三层依次回答“能否表达”“是否发生”“是否满足要求”。任一层缺失，结论都只能停留在更低的可信等级。

> **可生成表示候选路径存在，可执行和有效需要额外证据。**

### 4.3 中间态射的吸收

Prompt 技巧、工作流、Agent 编排、索引、外部记忆、脚手架、工具封装和人工流程，都可以看作连接输入与结果的中间态射。

当模型能力增强后，原本由中间层承担的部分工作可能被模型直接处理。若压缩中间层不会破坏外部边界、权限控制和独立验证，则可以减少中间对象；仍承担独立职责的部分应继续保留。

### 4.4 隔离审查

生成结果是候选对象，审查是独立的验证态射。重要结果生成后，应开启新的审查会话，不沿用生成会话的结论，重新读取原始目标、约束、代码、文档和验证结果：

```text
原始目标 ──生成复合──→ 候选结果
    │                    │
    └──独立验证复合──────→ 证据与结论
```

### 4.5 能力编排

遇到需求时，先寻找成熟工具、库、平台和仓库提供的已有能力，把它们当作可复用的现成态射。拼好码负责连接、适配、编排和表达业务规则；只有关键约束无法满足时，才新增核心态射，并限定它的职责。

```text
需求对象 → 能力识别 → 成熟态射组合 → 适配边界 → 业务结果 → 验证证据
```

## 5. 运行模型

### 5.1 从问题到证据

Vibe Coding 是把一个问题逐步变成已验证结果，并根据反馈继续修正的复合路径：

```text
现实问题 X
  ↓ 识别、描述、约束
目标结构 S
  ↓ Model：理解、推理、生成
候选方案 C
  ↓ Harness：上下文、工具、权限、执行循环
结果状态 S'
  ↓ 观察、测试、审查、记录
证据 E
  ↺ 反馈：修正目标、约束、计划与行动
```

### 5.2 正向构造与反向审查

正向路径从输入构造结果：

$$
X\xrightarrow{I}S\xrightarrow{M}C\xrightarrow{T_H}S'。
$$

反向路径从验收标准和结果检查条件：

$$
E\xleftarrow{V_\Gamma}S'\xleftarrow{T_H}C\xleftarrow{M}S\xleftarrow{I}X。
$$

两条路径使用相同的对象和态射定义，便于发现输入丢失、边界漂移和验证缺口。

## 6. 证明与推导

### 6.1 引理 6.1（路径可复合性）

**引理。** 在固定环境 $H$ 与契约 $\Gamma$ 下，若部分映射 $I$、 $M$、 $T_H$、 $V_\Gamma$ 在各自成功域上的相邻端点匹配，则在该成功域上复合 $V_\Gamma\circ T_H\circ M\circ I$ 存在。

**证明。** 在成功域上， $I$ 与 $M$ 可复合，所得映射与 $T_H$ 可复合，所得映射再与 $V_\Gamma$ 可复合。由范畴的结合律，复合括号的选择不影响最终态射。若失败状态未被纳入对象和态射定义，结论不延伸到失败域。证毕。

### 6.2 命题 6.2（验证路径条件）

**命题。** 在本文工程模型中，固定执行环境 $H$ 和原始契约 $\Gamma$。若候选方案 $C$ 经执行态射得到结果状态 $S'$，验证态射生成证据 $E$，验证过程满足来源独立性，并且：

$$
T_H(C)=S',\quad V_\Gamma(S')=E,\quad E\models\Gamma,\quad \mathrm{Ind}(V_\Gamma;\Gamma,S')
$$

则结果可以标记为“在给定契约和环境下已验证”。

本命题中的“独立验证”由 $\mathrm{Ind}$ 约束：验证器必须重新读取原始契约 $\Gamma$ 和实际结果对象或其可追溯产物，结论不能只来自 Model 的自述。新开会话可以帮助隔离生成上下文，但会话切换本身不构成独立性证明。

**证明。** 执行态射提供结果状态，验证态射将结果状态与原始契约映射为证据。条件 $E\models\Gamma$ 表示证据满足给定契约， $\mathrm{Ind}$ 表示该判断具有规定的来源独立性，因此从目标到结果的路径和从结果到证据的验证路径均满足规定条件。该标记的有效范围限定在给定契约、环境和证据内。证毕。

### 6.3 证明范围

上述引理证明复合路径在形式上的可组合性，命题规定工程状态“已验证”的必要条件。它们不证明某个具体程序必然正确；具体程序仍需在目标环境中运行，并提供对应测试和审查证据。

## 7. 工程验证与质量约束

### 7.1 态射契约

每条关键态射至少应写清：

1. 输入对象。
2. 输出对象。
3. 前置条件。
4. 后置条件。
5. 失败路径。
6. 成功证据。

### 7.2 交换条件与机器门禁

能被确定性检查的要求，应落成测试、类型、schema、脚本、CI 或检查清单。机器门禁负责拦截路径不一致、依赖缺失、链接失效、配置错误和没有验收证据的结果。

### 7.3 人、模型、运行时与机器

1. **人负责方向：** 确定目标、价值、约束、取舍和最终判断。
2. **Model 负责候选：** 理解上下文、推理、生成方案和提出行动意图。
3. **Harness 负责执行：** 管理上下文、工具、权限、记忆、执行循环和反馈。
4. **机器负责校验：** 按确定性规则检查结果，条件不满足时直接失败。

### 7.4 最小验证路径

```text
目标与约束
  → 候选方案
  → 执行结果
  → 独立审查
  → 机器门禁
  → 可追溯证据
```

缺少任一关键环节时，结果只能保留为候选状态，不能进入已验证状态。

## 8. 讨论与适用边界

### 8.1 范畴论的职责

范畴论为本项目提供统一的描述语言，帮助识别对象、标记变化、连接步骤、比较路径和组织反向检查。

### 8.2 工程验证的职责

范畴论本身不能替代程序运行、权限判断、测试执行、性能测量、安全审查或人工验收。形式上清楚的态射，仍需现实证据证明它能够运行并产生预期结果。

### 8.3 适用原则

- 先把真实对象和边界写清，再引入符号。
- 先说明输入、输出和验证，再讨论抽象结构。
- 只保留能帮助组合、检查或反向追溯的概念。
- 发现抽象无法解释实际行为时，回到输入、环境、权限和结果重新检查。

### 8.4 可证伪条件

出现以下任一情况时，应判定当前抽象或实现需要修正：

1. 无法明确指出态射的输入或输出。
2. 同一验收标准在不同路径上得到不一致结果。
3. 生成结果无法在目标环境中执行。
4. 验证依赖生成会话自己的口头结论。
5. 关键结果缺少可重复的测试、日志、diff 或其他证据。

## 9. 结论与展望

### 9.1 结论

本教程的核心路径可以压缩为：

$$
对象\to态射\to复合\to恒等\to交换图\to对偶审查\to证据。
$$

范畴论在本分支中承担根结构：对象承载问题与结果，态射表达变化，复合组织行动，恒等保持结构，交换图检查一致，对偶支持反向推理。

范畴论负责描述关系和一致性；运行环境、工具、权限、测试和人工验收负责确认结果。两者共同构成可执行、可检查、可回溯的 Vibe Coding 闭环。

### 9.2 展望

后续研究可以进一步形式化工具调用、权限边界、状态转换、证据强度和不同验证器之间的组合关系，并为具体工程域建立可复用的范畴模型。
