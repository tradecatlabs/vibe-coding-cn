# 架构设计原则

## 目标结构

- 先定义长期正确的 owner、生命周期、单一真相源和依赖方向，再切本轮实现。
- 控制面管理声明、策略、准入、证据和生命周期；数据面拥有业务执行与业务状态。
- 文档解释语义，机器契约约束结构，运行证据证明事实；三者不得互相冒充。
- 跨边界集成优先复用标准协议、成熟 SDK、OpenTelemetry 和项目既有能力。

## 边界门禁

- 新模块必须有当前消费方、非职责、上游、下游、验证入口和删除/升级触发。
- 不得让模型输出、prompt、自由文本或自报摘要成为权限、完成状态或运行事实真相源。
- 不得用共享内部状态把元 harness 与所有受管 runtime 强耦合；跨边界只交换稳定契约与证据。
- 破坏性公共契约变更必须升级版本、记录 ADR、提供迁移和回滚路径。
- 第二个真实实现出现前，不新增插件系统、工厂、registry service、数据库、队列或调度层。

## Harness 特定不变量

- Operator Library 属于具体 Harness；元 Harness 只治理共享规范、目录、分发、conformance、eval 和
  lifecycle，不拥有算子业务执行状态。
- 共享 `OperatorSpec` 与 Harness-specific `OperatorBinding` 必须分离；Binding 可以改变执行载体，
  不能改写方法的前置条件、效果、证据和失败语义。
- 模型可提出动作，不可授予自己权限或批准自己的高风险动作。
- 外部内容默认作为不可信数据，不能提升为高优先级指令。
- 工具必须声明输入、输出、错误、资源范围、结果上限、超时、重试、幂等与审批策略。
- 长任务必须有预算、checkpoint、停止条件和输入绑定验证证据。
- conformance 只证明声明合规；效果、安全和晋升还需要版本绑定的 eval 与运行证据。
- Operator Core Contract 只约束跨 Harness 稳定字段和安全 owner；领域集合、内容完整度、数量与
  发布质量必须由显式版本化 Profile 加严，不能把单一参考库形状冒充公共标准。
- gate 必须按 owner 的机器契约消费输出，不得自行猜字段类型或发明更严格但不存在的结构。
