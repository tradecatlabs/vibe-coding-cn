# ADR-0000 问题空间到解空间的最小闭环

## 背景

产品叙事希望保持“问题库 → 解库”的极简模型，但数学研究存在失败尝试、有限证据、局部结果和证明草稿。若 Agent 可以把一次生成直接写入解库，系统会把流畅答案误当数学事实。

## 目标终态

来源记录先归一为版本化 Problem；非可信 Agent 围绕 Problem 创建 Attempt 和候选 Result；受信验证链只把具有当前有效的独立直接验证与 statement faithfulness 证据的 proof 或 counterexample 纳入派生解库视图。

## 真实约束

- 已有 6012 条记录是来源观察，不能自动去重为数学问题。
- Lean/Mathlib 尚未安装，kernel-check 当前 fail-closed。
- 本地电子书、原始网页和上游 Git 缓存不能进入公开仓库或普通 CI。
- 用户需要产品层继续保持“问题库 → 解库”的简单表达。

## 惯性约束

旧 README 把 research/result 空间写作未来目标，但不存在需要保持的公共 API、持久数据或外部消费者；目录命名和空记录结构可以直接采用正确终态。

## 决策或结论

采用三个核心对象与空间：

1. `Problem`：规范化、版本化的研究问题；
2. `Attempt`：一次可追溯研究活动，其 lifecycle 不表达数学结论；
3. `Result`：使用 `outcome × evidence` 表达的候选成果。

`result-library/indexes/solutions.json` 是从 Result 派生的完整解投影视图，不是独立写入源。`/vibe-mathing` 未来只负责生成 Attempt 和 candidate Result，无权绕过验证门宣布解决。

证据不是 `numeric < symbolic < human < kernel` 的单一全序，而是验证能力集合形成的偏序。证据账本只追加，后续记录可以使早期证据失效；当前 outcome 必须据此重新派生，所以历史证据单调增长不等于结论不可撤回。

本决策的规范性结果已经压缩并发布为项目标准 [`VIBE-MATHING-SPEC v0.1`](../../standards/VIBE-MATHING-SPEC-v0.1.md)：R1 候选隔离、R2 验证准入、R3 证据守恒。本 ADR 解释“为什么”，标准定义“必须满足什么”，GATE-0002 和校验器负责“如何阻止违规晋升”。

### 顶层编排补充

在不改变上述三个数学核心对象的前提下，项目的顶层执行语言补充为 `Project → Workflow → Task → Step → Job`。它描述目标、任务网络、工作单元、操作和一次有界执行如何组织；它不是 `Problem → Attempt → Result` 的替代状态链，也不授予 Job、Worker 或调度器直接发布 Result 的权限。当前公共仓库只发布该模型的设计与边界，不宣称已有通用 DAG 调度器或五套持久化生命周期 schema。具体规则见 [`RESEARCH-LIFECYCLE-MODEL-v0.1.md`](../../standards/RESEARCH-LIFECYCLE-MODEL-v0.1.md)。

## Kill List

- 不创建“一问题一答案”的直接映射。
- 不把来源记录自动视为 canonical Problem。
- 不为初始空库引入数据库、图数据库、向量数据库、RDF 或多 Agent 编排。
- 不在 CI 中下载动态网页、上游仓库或本地文献。
- 不把 `solutions.json` 变成第二套人工维护真相源。

## 证据、Proof Point 与 Falsifier

- Proof point：JSON Schema、跨引用校验和派生索引能够接受独立验证的 proof/counterexample，并拒绝有限计算、自我审查、陈述失真和已失效证据。
- 当前证据：`python3 scripts/validate_research_spaces.py` 与 `python3 scripts/test_research_spaces.py`。
- Falsifier：任何 numerical/symbolic/partial/failed Result，或未独立验证、未通过忠实性审计、关键证据已失效的 proof，能够进入 `solutions.json`。

## 迁移切片

本轮只建立空真相源、Schema、校验器、负例、治理 Gate 和 CI。下一轮用三个垂直样例校准语义，再实现 `/vibe-mathing` 总控。
